# HumanThread 总体设计

> 版本：v0.1
> 状态：方向基线
> 更新时间：2026-05-20

## 1. 北极星目标

HumanThread 是一个人机协同工作流编排系统，建立在一个核心判断上：

> 人是单线程执行器。人在任意时刻都应该只需要聚焦当前最需要自己处理的一个原子任务。

系统负责工作流状态、任务路由、上下文交接、本地环境恢复和团队状态可见性。人负责当前原子任务中的判断和执行。

HumanThread 不是普通待办工具，不是普通项目管理看板，也不是纯 AI Agent 平台。它的产品定位是：

> 面向 AI 辅助工作的“人类线程调度器”：把工作原子化、路由化、可恢复化，并在人和 AI 之间持续流转。

## 2. 核心概念

| 概念 | 定义 |
| --- | --- |
| 人类线程 | 一个只能同时处理一个活跃原子任务的人类执行器。 |
| 原子任务 | 可被分配、开始、完成、中断、跟进或路由的最小工作单元。 |
| 工作流 | 由原子任务组成的状态机或有向无环图。 |
| AI 执行器 | 可以摘要、分类、路由、执行或生成跟进任务的自动化步骤。 |
| AI 路由器 | 决定下一步、执行人、优先级或是否需要人类介入的决策层。 |
| 当前任务 | 当前占用某个人类线程的唯一任务。 |
| 任务队列 | 分配给某个人类线程、排在当前任务之后的任务列表。 |
| 团队面板 | 类似线程池监控，用于展示每个人当前状态、当前任务、队列长度和阻塞情况。 |
| 本地 Agent | 连接 HumanThread 与本地工作环境的三端客户端，必须兼容 macOS、Windows、Linux，负责打开目录、启动 Claude/Codex 或其他工具、监听终端状态并回传事件。 |
| 会话适配器 | 支持终端持久化、输出捕获和快速恢复的模块，初期优先通过 macOS/Linux/WSL 上的 tmux 实现。 |

## 3. 不可偏离的方向

任何重要功能都必须强化以下至少一项：

1. 减少人的上下文切换。
2. 让工作更原子化、更容易路由。
3. 让工作流状态可以自动向前推进。
4. 提升团队里每个人类线程状态的可见性。
5. 提升 AI 路由或 AI 执行能力。
6. 提升本地工作环境的恢复和接续能力。

如果一个功能只是让产品更像普通项目管理软件，但没有强化 HumanThread 的核心模型，应当延后，除非它是实现核心闭环的必要支撑。

## 4. 产品边界

### 4.1 范围内

- 项目和事项选择。
- 工作流模板创建和实例化。
- 原子任务生成和路由。
- 个人当前任务工作台。
- 团队状态可见。
- 任务事件日志和工作流历史。
- 基础 AI 路由和 AI 执行步骤。
- 兼容 macOS、Windows、Linux 的本地 Agent，用于打开目录、启动 CLI 工具、回传终端状态。
- 通过包装脚本或会话适配器集成 Claude/Codex CLI。
- 通过 tmux 或兼容机制实现会话持久化和恢复。

### 4.2 MVP 暂不做

- 完整 BPMN 兼容。
- 复杂无代码流程设计器。
- 企业级复杂权限矩阵。
- 第一天就实现完整跨平台终端持久化。
- 不经人确认就完全自动判断“AI 正在思考”还是“已经断线”。
- 计费、市场、公开 SaaS 包装。
- 与工作流路由无关的通用聊天助手能力。

## 5. 三层架构

HumanThread 固定为三层系统。MVP 可以只实现每一层的轻量版本，但架构方向不应改变。

### 5.1 HumanThread Core

职责：

- 管理用户、项目、事项、工作流模板、工作流实例、任务、队列和事件。
- 强制人类执行器的“单当前任务”模型。
- 在任务完成、中断、阻塞或需要跟进时推进工作流状态。
- 先实现规则路由，再演进到 AI 辅助路由。
- 存储任务上下文和完整事件历史。

### 5.2 Web 工作台

职责：

- 配置项目和事项类型。
- 通过选择项目和事项来启动工作流。
- 展示用户当前任务和任务队列。
- 提供任务操作：开始、完成、阻塞、中断、跟进、转交。
- 展示团队状态：当前任务、队列长度、状态、阻塞原因、最后更新时间。
- 展示工作流时间线和执行历史。

### 5.3 本地 Agent

职责：

- 将本地机器绑定到 HumanThread 用户。
- 以统一技术栈兼容 macOS、Windows、Linux 三端。
- 用托盘应用或悬浮窗显示当前任务。
- 打开配置好的项目目录。
- 启动 Claude CLI、Codex CLI 或其他配置工具。
- 为任务启动或恢复本地会话。
- 捕获终端状态、进程状态和用户主动触发的回调。
- 向 HumanThread Core 回传任务事件。

技术约束：

- 客户端采用 Electron + TypeScript/React（2026-09-12 由 Tauri 迁移），与 Web 工作台共享前端技术、类型定义和 API schema；Android 使用 Capacitor 壳复用 Web 工作台。
- Flutter 不作为首选，因为本项目更需要复用 Web UI、TypeScript 类型和 API 协议，而不是单独维护一套 Dart UI。

## 6. 关键数据模型

初始模型应保持克制，但必须保留长期方向。

| 实体 | 作用 |
| --- | --- |
| User | 人类执行器。 |
| Team | 一组人类执行器。 |
| Project | 业务项目或代码项目。 |
| MatterType | 项目下的事项类型，例如功能开发、缺陷修复、代码评审、发布、合同审核、数据清洗。 |
| WorkflowTemplate | 某类事项可复用的流程定义。 |
| WorkflowStepTemplate | 可复用的原子步骤定义，包含执行者类型和路由规则。 |
| WorkflowInstance | 一次具体工作流执行。 |
| Task | 分配给人或 AI 执行器的一个原子步骤。 |
| TaskQueue | 某个人类线程的任务顺序。 |
| TaskEvent | 追加式状态变更记录，用于审计和回放。 |
| LocalDevice | 运行本地 Agent 的本地机器。 |
| ToolSession | 与任务关联的 CLI 或终端会话。 |

## 7. 任务状态模型

MVP 状态：

| 状态 | 含义 |
| --- | --- |
| pending | 已创建，但未激活。 |
| active | 当前正在被人类线程或 AI 执行器处理。 |
| completed | 已完成，可以推进工作流。 |
| blocked | 无法继续，需要外部输入。 |
| interrupted | 执行在完成前被意外或主动中断。 |
| follow_up | 需要生成新的人类跟进任务。 |
| transferred | 已转交给其他执行器。 |
| cancelled | 已取消，不再参与正常流转。 |

任何状态转换都必须创建 `TaskEvent`。

## 8. 核心工作流闭环

第一个完整闭环是：

1. 用户选择项目和事项类型。
2. Core 创建工作流实例。
3. Core 创建第一个原子任务。
4. 被分配的人在 Web 工作台或本地 Agent 中看到一个当前任务。
5. 用户开始任务。
6. 如果需要本地执行，本地 Agent 打开目录，并通过包装脚本或会话适配器启动 Claude/Codex。
7. CLI 完成、中断、超时或用户操作都会回传任务事件。
8. Core 更新任务状态。
9. Core 将工作流路由到下一个人类步骤或 AI 步骤。
10. 团队面板反映新的人类线程状态。

这个闭环是 MVP 的第一验收标准。

## 9. 本地执行策略

### 9.1 MVP

- 本地 Agent 必须在 macOS、Windows、Linux 三端都能打开项目目录。
- 本地 Agent 必须在 macOS、Windows、Linux 三端都能启动配置好的命令。
- CLI 包装器可以回传完成、中断和跟进。
- 对超时等不确定情况，不直接猜测，应询问用户确认。

### 9.2 后续

- macOS/Linux/WSL 通过 tmux 适配器实现持久会话。
- Windows 原生环境先降级为恢复工作目录并重新打开命令。
- 后续 Windows 高级支持可以考虑 ConPTY。
- Agent 可以根据项目、任务和工作流元数据重命名会话或窗口。
- Agent 可以捕获最终输出摘要，并附加到任务事件中。
- 当前已上线账号密码登录绑定方案：Web 工作台通过独立 `/login` 外部入口完成账号密码校验并写入签名会话，Mac 客户端填写邮箱、密码和设备名后由服务端自动授权设备；密码只在登录提交时一次性使用，不写入本地 binding 持久化数据。
- 绑定码过渡方案仍保留为兼容和排障路径：Web 工作台基于签名会话生成短期绑定码，Mac 客户端提交有效绑定码后仍可自动授权设备。

### 9.3 绑定演进

设备绑定演进分三层：

1. 兼容路径：手工 token + 手工设备信息，仅用于早期联调和排障。
2. 当前主路径：用户在 Web 或客户端通过账号密码完成登录，服务端基于登录身份和设备信息自动绑定。
3. 兼容路径：Web 工作台用签名会话确定当前用户并生成 10 分钟有效的绑定码，客户端提交有效绑定码后自动授权设备。

后续当多用户、多公司权限继续完善后，绑定流程应继续收敛为：

1. 用户先在客户端登录，当前已不保存密码；后续继续补齐短期登录 token 和刷新机制。
2. 客户端拿到登录态后请求设备接入。
3. 服务端基于用户身份、公司上下文和设备指纹创建或复用 `LocalDevice`。
4. 客户端保存设备 token，但不再要求用户手工填写 Team ID、User ID、API Token 和 Device ID。
5. Web 工作台保留设备授权/撤销入口，并以用户和设备名为主要展示信息。

## 10. AI 策略

### 10.1 MVP

- 默认使用规则路由。
- 当输入和输出足够约束时，AI 可以执行简单步骤。
- AI 可以生成建议跟进任务，但模糊情况必须由人确认。

### 10.2 后续

- AI 将高层事项拆解成原子步骤。
- AI 根据团队负载和历史数据推荐执行人和优先级。
- AI 从工具输出中检测阻塞、中断或跟进状态。
- AI 根据重复执行历史优化工作流模板。

## 11. MVP 验收标准

第一版只有满足以下条件才算有效：

1. 用户可以创建或选择项目和事项类型。
2. 启动事项后会创建工作流实例和第一个任务。
3. 用户界面以一个当前任务作为主工作项。
4. 完成当前任务后，工作流可以自动推进。
5. 团队面板能展示每个用户的当前状态和当前任务。
6. 本地 Agent 可以打开任务对应的项目目录，并启动配置好的 CLI 命令。
7. CLI 包装器或本地回调可以将任务标记为完成、中断或跟进。
8. 每一次状态变化都会记录为事件。

## 12. 长期方向

HumanThread 应从开发工作流工具成长为通用人机协同工作流 SaaS：

1. 先从 AI 辅助开发切入，因为 Claude/Codex 的中断、恢复和跟进是明确高价值场景。
2. 泛化工作流引擎和任务模型。
3. 扩展本地 Agent 集成能力。
4. 增加 AI 路由和工作流优化。
5. 增加团队分析和企业级管控。
6. 包装成 SaaS、私有化部署或团队本地部署。

长期护城河不是任务列表，而是以下组合：

- 人作为单线程执行器的模型。
- 原子化工作流路由。
- AI 辅助任务拆解和路由。
- 本地环境接续能力。
- 团队状态可观测性。
