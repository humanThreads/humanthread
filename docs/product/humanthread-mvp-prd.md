# HumanThread MVP PRD

> 版本：v0.1
> 状态：MVP 产品需求基线
> 更新时间：2026-05-18
> 上级文档：`docs/product/humanthread-overall-design.md`

## 1. MVP 目标

MVP 的目标不是做完整项目管理系统，而是验证 HumanThread 的核心闭环：

```text
选择项目/事项
  -> 创建工作流实例
  -> 创建原子任务
  -> 人只看一个当前任务
  -> 通过 Web 或本地 Agent 执行
  -> 回传任务状态
  -> 自动推进工作流
  -> 团队可见当前状态
```

只要这个闭环不能顺畅运行，就不应优先做复杂流程设计器、计费、权限矩阵或数据报表。

## 2. MVP 用户

### 2.1 个人执行者

典型用户：开发者、运营、审核人员、客服、项目执行成员。

核心诉求：

- 不想同时盯多个项目、群消息和任务列表。
- 希望系统告诉自己当前最该处理哪件事。
- 希望处理完成后，系统自动把流程交给下一个人或 AI。
- 希望需要本地执行时能一键打开正确项目和工具。

### 2.2 团队负责人

典型用户：技术负责人、项目负责人、运营负责人。

核心诉求：

- 想知道每个人现在在做什么。
- 想知道任务卡在哪里。
- 想让流程自动流转，而不是靠人手动催。
- 想减少成员在多任务之间频繁切换造成的损耗。

### 2.3 AI/工具执行器

不是自然人用户，而是系统中的执行单元。

核心作用：

- 执行受约束的自动步骤。
- 提取摘要、判断结果、生成跟进建议。
- 在不确定时把任务路由回人类。

## 3. MVP 核心场景

第一个演示场景固定为“AI 辅助开发任务”。

示例流程：

```text
创建开发事项
  -> 人类确认需求
  -> 本地 Agent 打开代码仓库并启动 Claude/Codex
  -> CLI 执行回传完成/中断/跟进
  -> 人类验收结果
  -> 工作流完成
```

选择该场景的原因：

- 本地目录、CLI、会话恢复和状态回调需求明确。
- 能直接体现 HumanThread 与普通待办工具的差异。
- 后续可以泛化到代码评审、发布、客服工单、合同审核、数据处理等流程。

## 4. 功能范围

### 4.1 项目管理

MVP 需要支持：

- 创建项目。
- 编辑项目名称、描述、本地目录路径。
- 查看项目列表。
- 选择项目来发起事项。

字段建议：

| 字段 | 说明 |
| --- | --- |
| 项目名称 | 展示用名称。 |
| 项目描述 | 项目背景。 |
| 本地目录 | 本地 Agent 用于打开目录或启动 CLI。 |
| 默认命令 | 例如 `codex`、`claude` 或自定义命令。 |

### 4.2 事项类型

MVP 需要支持预置事项类型，不要求做复杂配置器。

第一批事项类型：

| 事项类型 | 用途 |
| --- | --- |
| 开发任务 | 从需求确认到本地 CLI 执行再到人工验收。 |
| 缺陷修复 | 从问题确认到本地修复再到验证。 |
| 代码评审 | 从评审发起到 AI 辅助检查再到人工确认。 |

MVP 可以先用静态配置定义事项类型和工作流模板。

### 4.3 工作流实例

当用户选择项目和事项类型后，系统创建一个工作流实例。

需要支持：

- 生成工作流实例编号。
- 记录所属项目和事项类型。
- 根据模板生成第一个原子任务。
- 展示工作流当前状态。
- 展示工作流时间线。

### 4.4 原子任务

任务是 HumanThread 的核心对象。

MVP 任务必须支持：

- 分配给人类用户或 AI 执行器。
- 同一用户只能有一个主当前任务。
- 支持状态变化。
- 支持上下文信息。
- 支持事件历史。

任务展示字段：

| 字段 | 说明 |
| --- | --- |
| 任务标题 | 当前要做什么。 |
| 所属项目 | 来自哪个项目。 |
| 所属事项 | 来自哪个事项实例。 |
| 执行说明 | 用户应该怎么处理。 |
| 当前状态 | pending、active、completed 等。 |
| 指派对象 | 人或 AI。 |
| 本地上下文 | 目录、命令、会话信息。 |

### 4.5 个人当前任务工作台

这是 MVP 的核心界面。

必须做到：

- 当前任务在视觉上明显高于普通列表。
- 用户进入后首先看到当前任务，而不是复杂项目看板。
- 当前任务提供明确动作按钮。
- 排队任务可以查看，但不能喧宾夺主。

任务动作：

| 动作 | 结果 |
| --- | --- |
| 开始 | 将任务设为 active，并记录事件。 |
| 完成 | 将任务设为 completed，并触发流程推进。 |
| 阻塞 | 将任务设为 blocked，并记录原因。 |
| 中断 | 将任务设为 interrupted，并保留上下文。 |
| 跟进 | 创建或标记 follow_up 任务。 |
| 转交 | 将任务分配给其他用户。 |
| 打开本地 | 调用本地 Agent 打开目录或 CLI。 |

已落地能力：

- `开始`、`完成`、`阻塞`、`中断` 已支持。
- `跟进`、`转交` 已支持。
- 首页已提供快速创建事项入口和当前任务动作入口。
- 阻塞与中断原因会写入事件时间线。
- 跟进与转交也会写入事件时间线。
- CLI 回调事件的命令、状态、退出码、耗时已可在时间线中展示。
- 工作流详情可通过时间线 API 读取事件序列。

### 4.6 团队状态面板

团队面板用于体现“线程池监控”。

MVP 展示：

| 字段 | 说明 |
| --- | --- |
| 用户 | 团队成员。 |
| 当前状态 | 空闲、处理中、阻塞、离线。 |
| 当前任务 | 正在处理的任务标题。 |
| 所属项目 | 当前任务所属项目。 |
| 队列长度 | 排队任务数量。 |
| 最后更新 | 最近状态更新时间。 |

MVP 不需要复杂绩效分析，但必须能让团队知道每个人“现在被什么占用”。

### 4.7 本地 Agent

MVP 的本地 Agent 先做轻量能力，但客户端必须兼容 macOS、Windows、Linux 三端。

技术约束：

- 首选 Tauri + TypeScript/React。
- 尽量复用 Web 工作台的 UI 组件、共享类型和 API schema。
- 三端都必须支持基础能力：绑定用户、展示当前任务、打开目录、启动命令、回传事件。
- 会话持久化允许平台差异：macOS/Linux/WSL 优先 tmux，Windows 原生先降级。

必须支持：

- 绑定用户身份。
- 拉取或接收当前任务。
- 展示当前任务。
- 打开项目本地目录。
- 启动配置命令。
- 回传本地事件。

当前服务端进展：

- 已提供 `GET /api/agent/current-task`，可返回本地 Agent 所需的当前任务、项目目录和默认命令。
- 已提供 `POST /api/agent/device/register`，可完成设备登记、设备 token 复用与授权状态返回。
- 已提供 `POST /api/agent/events`，可回传 `local_opened`、`command_started`、`command_exited` 事件。
- 本地命令执行已改为 Agent 受控执行，任务结束后可自动回传 `command_exited` 与退出码。
- 本地 Agent 的任务轮询与事件回传必须携带 Bearer token，服务端会校验 token 与目标用户身份是否匹配。
- 服务端已提供最小本地 Agent token 轮换接口 `POST /api/agent/token`，管理 Web 首页也已提供一次性明文 token 轮换面板。
- 本地事件会写入 `TaskEvent` 时间线；设备信息会写入 `LocalDevice`。

当前客户端进展：

- 已创建 `apps/local-agent` 桌面端骨架，采用 `Tauri + React + TypeScript + Vite`。
- 已支持保存本地绑定配置：服务地址、团队、用户、设备 ID、设备名、轮询间隔。
- 已支持保存本地 API Token，并在客户端请求时自动携带认证头。
- 已支持轮询拉取当前任务，并展示项目、工作流、本地目录、默认命令。
- 已支持“打开项目目录”“在此处打开终端”和“启动命令”三个动作；命令输入可覆盖项目默认命令。
- 已支持命令模板配置，可将 `taskId`、`projectId`、`workflowInstanceId` 注入到包装命令中。
- 已补齐 Tauri 命令层占位，实现跨平台目录打开、终端打开和命令启动的最小策略。
- 已在 macOS 本机完成 `verify:e2e`、`tauri:dev -- --no-watch` 与 `tauri:build -- --debug` 验证；`Windows / Linux` 仍待目标机器补做实机验证（2026-09-12 起桌面端迁移 Electron，命令与验证方式见 `docs/architecture/local-agent-electron-migration.md`）。

后续登录化绑定要求：

- 当前手工填写 `API Base URL`、`Team ID`、`User ID`、`Device ID`、`API Token` 的方式只作为 MVP 联调方案。
- 在多用户、多公司权限功能完成后，本地 Agent 必须改为用户登录优先：用户在客户端完成登录后，系统自动确定用户身份、公司/项目可见范围和本机设备身份。
- 登录后服务端应自动创建或复用 `LocalDevice`，并返回设备 token；客户端保存登录态和设备 token，不再要求用户手工复制 API Token。
- Web 工作台仍需要保留设备授权/撤销入口，但授权对象应以“用户 + 设备名 + 平台 + 最近请求时间”展示，避免暴露底层 token 和 ID 概念。
- 管理员或用户可以撤销设备授权；撤销后客户端需要提示重新登录或重新申请设备授权。

暂不要求：

- 完整三端一致的会话恢复。
- 完整窗口管理。
- 完整终端模拟器。
- 完全自动判断 AI 思考或断线。

### 4.8 CLI 回调

MVP 需要一个包装命令，例如 `ht-run`。

基本能力：

- 启动真实命令，例如 `ht-run --task <id> -- codex`。
- 捕获退出码。
- 捕获运行时长。
- 捕获最后若干行输出。
- 退出码为 0 时默认回传完成。
- 非 0 或 Ctrl+C 时默认回传中断。
- 提供手动标记跟进的方式。
- 支持显式覆盖本次回调状态为 `follow_up`。

超时判断：

- MVP 不直接自动判定断线。
- 当前实现先采用保守降级：长时间无输出时，终止进程并自动回传 `follow_up`。
- 后续再升级为交互式确认：继续等待、标记中断、标记跟进。

## 5. MVP 不做什么

MVP 明确不做：

- 通用低代码流程编辑器。
- 完整多租户 SaaS。
- 复杂角色权限。
- 复杂报表。
- 移动端 App。
- 完整 Windows 原生会话恢复。
- 自动学习型 AI 路由。
- 所有 CLI 工具的深度适配。

这些能力应在核心闭环验证后再进入 1-n 阶段。

## 6. 用户故事

### 6.1 发起事项

作为团队成员，我希望选择一个项目和事项类型后，系统自动创建工作流和第一个任务，这样我不需要手工拆流程。

验收：

- 可以从项目列表选择项目。
- 可以选择事项类型。
- 点击创建后生成工作流实例。
- 系统生成第一个任务并分配给对应执行者。

### 6.2 处理当前任务

作为执行者，我希望只看到当前最该处理的一件任务，这样我不会被多个任务分散注意力。

验收：

- 当前任务在主界面突出展示。
- 排队任务不抢占当前任务视觉层级。
- 当前任务可以开始、完成、阻塞、中断、跟进、转交。

### 6.3 自动流转

作为团队负责人，我希望一个任务完成后，系统自动把流程推进到下一步，这样不需要人工催办。

验收：

- 完成任务后创建任务事件。
- 工作流找到下一步。
- 下一步任务被创建或激活。
- 被分配用户的当前任务或队列更新。

### 6.4 本地执行

作为开发者，我希望处理开发任务时一键打开对应代码目录和 Claude/Codex，这样我不需要手动找目录、切终端、复制上下文。

验收：

- 当前任务包含项目目录和默认命令。
- 点击打开本地后，本地 Agent 打开目录。
- 本地 Agent 可以启动配置命令。
- 本地事件回传到任务时间线。

### 6.5 CLI 状态回调

作为开发者，我希望 Claude/Codex 执行完成或中断后自动同步任务状态，这样我不用回网页手动补状态。

验收：

- `ht-run` 可以启动真实 CLI。
- CLI 正常退出后任务变为 completed。
- CLI 中断后任务变为 interrupted。
- 用户可以标记 follow_up。
- 状态变化写入 `TaskEvent`。

### 6.6 团队可见

作为团队负责人，我希望看到每个人现在正在做什么，这样我能判断流程瓶颈和人员占用。

验收：

- 团队面板展示所有成员。
- 每个成员显示当前状态、当前任务、项目和队列长度。
- 任务状态变化后团队面板更新。

## 8. 指标

MVP 阶段应跟踪以下指标：

| 指标 | 意义 |
| --- | --- |
| 事项创建数 | 是否有人真的发起流程。 |
| 任务完成率 | 工作流是否能闭环。 |
| 平均任务处理时间 | 原子任务粒度是否合适。 |
| 中断任务数 | 本地/AI 执行是否稳定。 |
| 跟进任务数 | AI 或流程是否经常需要人类介入。 |
| 用户当前任务为空的时间 | 是否存在任务断流。 |
| 团队队列长度 | 是否存在人员瓶颈。 |

## 9. MVP 成功标准

MVP 不是看功能数量，而是看闭环是否成立。

成功标准：

1. 至少一个 AI 辅助开发流程可以端到端跑完。
2. 至少两个用户之间可以流转任务。
3. 用户可以只看当前任务完成主要工作。
4. 本地 Agent 可以打开目录并启动 CLI。
5. CLI 结果可以回传任务状态。
6. 团队负责人可以看到成员当前状态。
7. 所有状态变化都有事件记录。

如果以上 7 条不成立，应继续打磨 MVP，而不是进入复杂扩展。
